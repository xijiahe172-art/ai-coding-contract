# AI Coding Contract · AI 编程契约

> 把「别乱改、别乱说、别啰嗦」写成 AI 每次开口前都要遵守的契约。
> A five-clause contract that keeps coding agents scoped, evidenced, and terse.

AI 编程助手已经能独立完成多步改动，但它默认的行为模式，和评审一段代码的真实成本并不匹配：它会顺手改掉你没让它改的部分；会把仍然成立的注释一起重写；会在没有触发条件和行号的情况下断言「这就是 bug」；会在下一轮毫无新证据地推翻自己刚说过的结论；还会把未改动的代码整段贴回来、用「接下来我将……」把对话填满。单看每一次，浪费的只是几分钟；放进一个真实的、长期维护的仓库，它持续消耗的是评审者的注意力和对结论的信任——而这两样东西，是团队里最难补回来的。

这个项目只做一件事：把这五条约束固化进 AI 的系统提示词，让它每次动手前先受约束——范围先说清，证据先给出，输出按格式，节奏听指挥。

## 背景：AI 辅助编程的六类失控

这六类失控不是模型能力问题，而是**默认行为与工程成本结构不匹配**的结果。它们都出现在"模型已经足够强、你开始放心让它改真代码"之后。

| 典型症状 | 发生在哪一步 | 真实代价 |
| --- | --- | --- |
| 顺手重构、顺手优化、动了没让动的文件 | 动手时 | 评审面被放大到无法逐行确认，回滚成本上升 |
| 重写或删除仍然成立的注释 | 编辑时 | 丢失意图与历史背景，下一次改动踩到坑 |
| 新增注释只是复述代码在做什么 | 编辑时 | 注释随代码一起腐化，失去维护价值 |
| 没有触发条件、位置、复现方式就断言「已确认的 bug」 | 汇报时 | 把人派去修一个不存在的问题，最贵的一类浪费 |
| 下一轮无新证据地推翻上一轮结论 | 追问时 | 结论不可追溯，所有历史结论都要重新验证 |
| 贴回大段未改动的代码、输出过程旁白、解释冗长 | 交付时 | 评审者要在噪音里找那三行真正的改动 |

## 规则详解：六个维度与五条条款的对应关系

六维度是**从痛点侧切分**的视角，五条条款是**给模型看的约束**。两者不是一一对应：第 3 条同时覆盖「证据」和「稳定」两个维度。

| # | 维度 | 典型症状 | 对应条款 | 契约要求的行为 |
| --- | --- | --- | --- | --- |
| 1 | 变更范围 | 顺手重构、顺手优化、改了没让改的文件 | 第 1 条 | 动手前用 ≤3 行说明：改哪个文件/哪个函数、范围多大、影响哪些调用方；声明范围之外的代码不碰 |
| 2 | 注释与既有逻辑 | 重写仍然成立的注释、新注释复述代码 | 第 2 条 | 注释只在它所描述的逻辑本身被修改时才改；新增注释只讲「为什么这么写」 |
| 3 | 结论的证据 | 拍脑袋说「这是 bug」「已确认」 | 第 3 条（前半） | 触发条件 + 具体位置（文件 + 行号）+ 验证方式，三项齐全才允许说 confirmed；缺任何一项只能标 suspected |
| 4 | 结论的稳定性 | 下一轮无新证据地推翻上一轮结论 | 第 3 条（后半） | 已给出的结论不因追问或措辞而改口；要推翻必须提供新证据 |
| 5 | 输出形态 | 贴大段未改动代码、过程旁白、解释冗长 | 第 4 条 | 改动用 diff / 改动片段；纯分析不强制 diff；解释 ≤3 句；不写「接下来我将……」 |
| 6 | 执行节奏 | 该连跑时反复请示，或该确认时越权连跑 | 第 5 条 | 授权范围内连续自动执行，不逐步问「是否继续」；授权边界由用户声明 |

### 规则全文（可直接复制）

```text
1. 改动前用≤3行说明:改哪个文件/哪个函数、改动范围、是否影响其他调用方。
   未经确认不得修改声明范围之外的代码,不得顺手"优化"未要求的部分。

2. 不改写、不删除已有代码注释,除非该注释描述的逻辑本身被修改。
   新增注释只讲"为什么这么写",不复述代码在做什么。

3. 分析bug时，必须给出：触发条件、具体位置（文件+行号）、你验证过的方式。
   三项缺任何一项，只能标记为“可疑点（suspected）”，不得断言为已确认（confirmed）的bug。
   已给出的结论,没有新证据不得在后续轮次里无理由推翻。

4. 输出规则:
   - 修改已有文件用diff/改动片段，不贴未改动的完整内容
   - 新建文件允许输出完整内容
   - 删除文件只需一句话说明，不用diff
   - 纯分析、未修改代码的场景，不强制diff格式
   - 代码后的解释控制在3句以内,不必要不解释
   - 不输出"接下来我将..."这类过程性旁白

5. 我会说明哪些操作可以连续自动执行,哪些需要停下确认;
   按此执行,不要对已授权范围内的操作逐步询问"是否继续"。
```

## 使用方法

三个层次，按生效范围从大到小。**先想清楚你要的是「所有项目都生效」还是「只在这个仓库生效」**——多数人两个都要，而它们不冲突：全局放一份通用的，项目级按需覆盖。

### 方式一：直接进系统提示词（最彻底）

任何能改 system message 的入口都适用。

API 调用：

```json
{
  "model": "<your-model>",
  "messages": [
    { "role": "system", "content": "<把上面的规则全文粘贴到这里>" },
    { "role": "user", "content": "<你的任务>" }
  ]
}
```

### 方式二：全局指令文件 / 全局自定义指令

大多数编程助手都提供「全局指令」「custom instructions」「user rules」一类的设置项，把规则全文填进去即可，之后每个新会话自动带上，不用手动粘贴。不同工具对这类配置的存放路径和优先级各不相同，以各自官方文档为准。

### 方式三：项目级指令文件

把规则全文放进仓库根目录的指令文件（`AGENTS.md`、`CLAUDE.md`、`.cursorrules`、`copilot-instructions.md` 等，取决于你用的工具）。好处是随代码一起版本化、一起评审；代价是只对这个仓库生效。

### 三个坑

- **只在新会话生效。** 系统提示词和指令文件通常在会话建立时读取，改完设置请新开一个对话验证。
- **优先级方向别搞反。** 项目级指令通常比全局更具体、更容易被采纳，因此不要在两处各维护一份不同版本。
- **按需裁剪。** 六条约束里，第 1、3 条的收益最大、代价最低；如果你的任务是探索性的，可以先只保留这两条。

## 实测效果

前提：同一模型、同一仓库、同一任务，唯一变量是有没有这份契约。以下为**定性对比，不是量化基准**——效果随模型、任务规模和你的追问方式变化。

### 案例一：给一个网络客户端的失败分支加一行诊断日志

| | 无契约 | 有契约 |
| --- | --- | --- |
| 第一步 | 直接开始改代码 | 先给 3 行范围声明：改哪个函数、新增几条语句、哪些调用方不受影响 |
| 改动面 | 顺手重构了错误处理分支，顺带调整了相邻模块 | 只加日志语句，原有错误处理逐字未动 |
| 交付形态 | 整段未改动的文件被贴回，真正的改动要靠人找 | 只给 diff |
| 解释 | 大段「接下来我将……」的过程旁白 | ≤3 句，只讲为什么这么写 |

### 案例二：一份偶发故障的报告

- **无契约**：「已确认是并发 bug，是竞态导致的。」——没有触发条件，没有位置，没有验证方式。追问一轮后，又改口成「应该是配置问题」。
- **有契约**：「可疑点（suspected）：触发条件是 A 与 B 同时发生；位置 `文件:行号`；我这样验证过：……三项中缺『稳定复现』，因此不能标 confirmed。」下一轮给出新证据后，才升级为 confirmed。

预期收益（同样是定性的）：评审时间下降、结论可追溯、跨轮次不再自我否定。**契约不会提高模型的能力，也不保证代码正确**——它约束的是过程与表达，不是正确性证明。

## 适用场景

- 长期维护、多人评审的生产仓库：改动面可控比改得快更值钱。
- 对变更敏感的场景（合规、审计、稳定性关键路径）：需要每一次改动都有可记录的声明与依据。
- 长会话协作：要求结论跨轮次稳定、可追溯，不想每轮重新建立共识。
- 带新人 / 教学：想直观看到「有经验的工程师如何交付一次改动」。

## 不适用场景

- 一次性脚本、原型、探索性重构：第 1 条的范围声明在这里几乎全是开销。
- 开放式设计与头脑风暴：过早收敛会压掉本来有价值的方案。
- 微任务（改错别字、加一行输出）：形式化成本高于收益。
- 无人值守的长跑自动化：第 5 条要求由你声明授权边界，它的前提是「有人在指挥节奏」。
- 追求代码正确性的场景：契约管纪律与表达，不替代测试、类型系统与评审。
